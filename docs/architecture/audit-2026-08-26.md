# Architecture Audit — 2026-08-26

## Scope and evidence

This audit covered the complete imported application tree, runtime dependency
graph, API routes, client query flow, evidence and safety contracts, tests,
repository history boundary, public documentation, and WebMCP release needs.
It distinguishes implemented local evidence from supported-browser, live-source,
CI, deployment, and public-submission evidence.

## Conclusion

Sky to Porch did not need a broad rewrite. Its evidence contracts, source
adapters, deterministic evaluator, map, and failure-state model were already
the right foundation. The necessary refactor was to put one application layer
between both callers and that foundation:

    Human form -----\
                     > shared analysis controller -> evidence pipeline
    WebMCP tool ----/                    |
                                          -> one visible map and Insight state

The implemented vertical slice is therefore a product extension rather than a
parallel API wrapper.

## Findings and disposition

## IBM, Granite, and Claude decision

Active product code, API routes, environment configuration, UI status, and
runtime dependencies no longer depend on IBM, Granite, or Claude. Removing
those execution-path traces reduces confusion and eliminates a provider
migration that WebMCP does not require.

Historical attribution is intentionally retained in `PRIOR_WORK.md` and
`NOTICE`. Erasing it would weaken the prior-work boundary and make the
challenge record less truthful. The `.claude/` ignore entry is a defensive
local-file exclusion, not a runtime integration.

## Implemented WebMCP behavior

- One tool accepts a place or coordinates, hazard, optional concern, radius,
  date window, and question.
- Unknown fields and invalid coordinates, radii, or dates fail validation.
- Ambiguous geocoding returns `needs_place_choice` without starting analysis.
- Default dates select completed source periods rather than implying current
  conditions.
- Successful analysis synchronizes the visible selection, map, and Insight
  result; mobile moves to Insight.
- Tool output carries an untrusted-content annotation and is not labelled
  read-only because it deliberately changes page state.
- Tool responses stay within the current compact-output budget in deterministic
  tests.

Playwright injects a deterministic `document.modelContext` test double because
the bundled test browser is not proof of the challenge browser implementation.
This verifies application-owned behavior, not agent model quality or browser
availability.

## Remaining release gates

1. Use a challenge-supported browser/build where `document.modelContext` is
   present, then prove real discovery and execution without the test double.
2. Run model-backed selection and argument evals against the checked-in dataset;
   do not report deterministic dataset validation as a model-eval pass.
3. Run controlled live-source checks separately from fixture tests.
4. Obtain exact private-repository CI evidence for the implementation commit.
5. Review the human-agent workflow, video journey, and ambiguity copy with the
   product owner.
6. Request separate authorization before public visibility, deployment, or
   challenge submission.

## Commit strategy

Keep two meaningful commits in the sanitized repository:

1. the imported prior-work baseline;
2. one cohesive WebMCP implementation, refactor, tests, and documentation
   commit.

This is the minimum history that still makes old work and challenge work
unambiguous. Squashing those two together would reduce the count by one but
would damage the challenge boundary.
